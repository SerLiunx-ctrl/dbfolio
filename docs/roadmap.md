- 当前项：README 中英文切换、目录与界面示例已完成（用户最新指定，优先于 R05）；2026-09-30，应用版本仍为 v1.0.0-alpha.7，双语链接/锚点与五张截图路径检查通过，MongoDB 图已脱敏；此前 SQLite 文件拖入快速建会话也已完成并验证，两项随本次提交归档。

- 已完成：**4 / 39 项**。
- 上一轮按用户要求依次完成 R01 → R02 → R03。完成日期 2026-09-26，版本 0.178.0，代码提交 [a07fa00](https://github.com/SerLiunx-ctrl/dbfolio/commit/a07fa00699a26922cdb833dae7793bff7cf0e819)。本轮按用户要求实施 R04，并将每次代码改动生成安装包与正式便携版列为交付规则。

## 2. 实施与打标规则

1. 默认按 **R01 → R39** 的编号顺序推进；编号同时考虑优先级、依赖和可交付性。用户最新指定的任务或顺序优先，调整时记录原因，不静默跳项。
2. P0 为日常必需与发布基础；P1 为开发效率和结构变更管理；P2 为深化与特色能力；P3 为长期扩展。复杂度只是相对规模，不代表工期承诺。
3. 开始一项时，将该项状态改为「进行中」，同步更新顶部当前进行项。存在实际阻碍时标记「受阻」并写明原因和已完成范围。
4. 总览采用 `- [ ]` / `- [x]`。部分实现、仅构建通过或缺少关键验收时不勾选；详情可写「部分完成」「待验收」。完成范围不得悄悄缩小。
5. 满足该项验收及通用完成标准后，勾选总览，详情改为「已完成」，填写完成日期、应用版本、验证结果和代码提交（尚未提交时如实记录）。更新完成数量和下一项。
6. 每项同步更新 `design.md` 第 20 节实现状态和第 21 节变更记录；涉及使用方式或支持范围时更新 README。提交遵守 `feat:`、`fix:`、`docs:` 等类型前缀规则。
7. 建议每项形成可独立验证的交付；大项可拆内部步骤，但不能因某一步完成就把整个大项打勾。
8. P3 涉及跨引擎同步、更多平台或团队服务时，在实施前重新评估需求和技术边界，并明确更新设计决策。列入路线图不代表这些能力现在已经开放。

### 通用完成标准

- 明确支持的数据库、服务器版本、对象类型和不支持情形；不可用能力有合理提示。
- 遵守紧凑 UI 原则：小号控件、短间距、按需编辑；缩放后中文不裁切，深浅色和 OLED 主题可读。
- 写操作执行只读与数据库范围检查；计划、执行目标和实际结果明确，结果不确定时不自动重试。
- 长任务显示真实进度及取消状态；取消与回滚分开解释，大文件/大表操作控制内存占用。
- 验证相关精度与类型边界，包括大整数、Decimal、NULL、空串、时间及二进制；不要求无关功能重复全部测试。
- 按改动运行必要构建、自动测试和交互检查；涉及引擎行为时使用隔离测试库完成实测，并记录实际环境。缺少关键验证不能直接标记完成。
- 应用改动完成验证后生成并验证 NSIS 安装包及正式目录式 portable（目录和 ZIP）；测试 portable-fast 不能替代正式交付。纯文档变更无需重新打包。不能恢复单文件 EXE 分发。
- 文档、支持范围、已知限制与实际行为一致。

**状态：已完成｜类型：新增。** 独立导入页、流式预检、逐语句报告、隔离 MySQL 验收及 portable 验证完成。
